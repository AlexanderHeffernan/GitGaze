# Shared GitGaze client: review slice

The reference is macOS at `35de4505`. This is a draft migration, not a Windows release or a replacement for the production Mac app. It runs one checked-in dashboard, widget system and contribution calculation slice in two native hosts. The earlier all-WPF UI/data implementation is not part of this branch. The website remains independent; the optional shared leaderboard is a separate stack on this branch.

## Decision

Use a bundled, framework-free HTML/CSS/JavaScript client in [WKWebView](https://developer.apple.com/documentation/webkit/wkwebview) and [Edge WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). WPF here hosts WebView2; it does not render widgets or calculate metrics. AppKit owns the existing status item and transient popover. Win32 owns the notification icon, context menu and anchor. Assets are byte-for-byte identical, no remote UI navigation is allowed, and browsers can render a fixture without a bridge. Cost: Swift and .NET shells, two system browser engines to test, and servicing the self-contained .NET payload plus verifying the Evergreen Runtime on Windows. No bundled Chromium, web server or Node runtime is needed by desktop users.

- **Windows-only WPF** has good Win32 integration and no WebView dependency, but sharing queries still duplicates the renderer, calculations, refresh/cache and preferences. Rejected.
- **[Avalonia](https://docs.avaloniaui.net/docs/supported-platforms)** could own product logic and UI in .NET on both platforms. It requires a renderer rewrite, native shell interop to reproduce the AppKit popover, and support/packaging validation for Mac 14+ and both Windows architectures. The embedded renderer was exercised in the existing AppKit popover and also serves the browser demo without a second renderer or WASM runtime.
- **Swift core + native UIs** would reuse date logic and GraphQL. [Swift has both Windows architectures](https://www.swift.org/install/windows/) but not SwiftUI, AppKit, Combine, ServiceManagement, UserNotifications or Sparkle on Windows. Bridging a Swift library into a shared UI would add an ABI and runtime without preserving the current UI. Swift remains the oracle during migration, not a second maintained implementation behind the new hosts.
- **Electron/Tauri** can also share web UI. Electron adds bundled Chromium and a larger dual-architecture patch and signing surface; Tauri still uses WebView2/WKWebView and would add Rust and require re-establishing AppKit popover and Sparkle integration. Reusing the existing native Mac shell is the smaller first move.

## Native differences

Microsoft's [notification area](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area) has a fixed-size icon and owner-controlled overflow, not a variable-width status label. Do not force pinning. The intended design keeps six compact glyphs, with full text and optional streak in the tooltip rather than promising wide inline text. The slice only registers a static icon. It calls [Shell_NotifyIconGetRect](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyicongetrect) with callback position as fallback, clamps to monitor work area and handles [TaskbarCreated](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar#taskbar-creation-notification). Pinning, overflow, keyboard activation, display/DPI edges, Explorer restart and notification delivery still need real desktop checks. Windows sign-in, notification controls and user-consented Git integration are OS adapters, not platform-specific feature rules.

### Minimal migration order

1. Grow the shared product state behind the fixture contract. Keep GitHub tokens inside the native credential/HTTP boundary: one approved GraphQL endpoint, typed variables, no arbitrary execution requests and no token in the WebView, demo, cache or logs. Move scheduling/retries and display rules into shared code, not duplicated host implementations. The review bridge currently supports only snapshot, preferences in memory, and dismiss.
2. Mac reads existing `~/Library/Application Support/GitBar/dashboard.json` directly (Swift `Date` counts seconds since 2001-01-01), and adapts the existing `app.gitbar.mac` preference keys before doing any writes. Test exact read/write round trips and downgrade against a disposable copy. Preserve stored favourite order, widgets, hidden flags, theme, update/reminder and opt-in settings. Verify the `gh` viewer before using a different account's cached data after successful identity resolution; preserve offline use with its existing cache behavior. Do not migrate or store a GitHub token. All of this is a cutover contract, not implemented disk persistence in this slice.
3. Finish parity and real-platform acceptance. Keep the existing Mac release lane intact until a signed update preserves cache, preferences and continuity; then remove SwiftUI and obsolete Swift product semantics from the shipping client. Publish Windows using a separately approved release lane, not this review workflow.

## Reproduce

- `node --test SharedClient/core.test.js` verifies shared calendar and legacy preference/cache semantics.
- On a Mac with a GUI session, `bash scripts/compare-flyout.sh` captures both popover content views from the same fixture (not compositor screenshots). It replaces a disposable ad-hoc-signed 1.0.0 debug bundle with 1.0.1 at the same path, checks bundle ID, feed and public key, and relaunches with the isolated Swift Codable cache and defaults. The report measures programmatic open to laid-out fixture content with animation off; WebKit interactions are DOM-driven, not pointer or keyboard proof. The replacement is not a Sparkle update and does not exercise actual login items, Git hooks, notifications or credentials. `swift test && swift test -c release && ./scripts/build.sh && .build/GitGaze.app/Contents/MacOS/GitGaze --smoke-test` checks that the shipped Mac target remains intact.
- Windows review workflow publishes ARM64/x64 ZIP payloads, records their head and verifies native process architecture and bundled files. It does not exercise Explorer/UI. Extract the matching ZIP into a user-owned directory, open `GitGaze.exe` with Edge WebView2 Runtime installed, then use the overflow icon. Canned data is intentional; use no credentials. Check Open/Quit, Escape, outside click, context menu, reopen and Explorer restart. Delete the extracted directory when done. Windows on Arm x64 emulation is not native x64 desktop evidence.
- `python3 -m http.server --directory SharedClient 8000`, then open `/demo.html`. It loads only `fixture.json` and embeds the exact dashboard assets. It has no credential/storage hooks or native bridge calls; mutations reset on reload. Serve the folder at a trusted origin as local static assets rather than loading renderer JS from a moving feature branch.

## Local packaging and signing boundary

- From a clean checkout with Python 3.11+ and .NET 10, run `python3 scripts/package-windows.py VERSION --output .build/windows-distribution`. The versioned ARM64/x64 ZIPs include the self-contained .NET payload, commit ID and license. Check `SHA256SUMS` before distribution. The Windows user needs the matching Edge WebView2 Evergreen Runtime and GitHub CLI for live activity. These are unsigned extract-and-run packages, not installers. A trusted Windows release needs a publisher identity/service with Authenticode SHA-256 timestamping, validation of the signed payload and regenerated archive digests. No publisher has been established here.
- The existing Mac release command is `bash scripts/package-release.sh VERSION`. It still packages the SwiftUI default; it is not a shared-client production build. The existing Developer ID Application identity, Apple notarization authorization and matching Sparkle EdDSA private key must be supplied through the release keychain/CI. The public key and feed are already in `Info.plist`. Verify a real signed update from the current released app before switching the default; ad-hoc local replacement can only qualify isolated data and static identity compatibility.
- No further Windows desktop checks are scheduled. The owner manually confirmed the ARM64 fixture at `394d67a` (artifact `15001268753`). The independent notification-icon control passed on BigMac, but the app harness timed out in overflow; there is no automated desktop pass. Routine CI is package/process coverage only.
